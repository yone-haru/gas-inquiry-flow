# 問い合わせ管理・自動通知システム（GAS）

> Google フォーム→スプレッドシートの問い合わせ対応を自動化する Google Apps Script。中小企業の非エンジニア担当者向けに、通知・リマインド・エスカレーションを自動化する。ポートフォリオとして GitHub 公開する（詳細: `requirements-gas-inquiry-flow.md`）。

## 技術スタック
- 言語: JavaScript（GAS / V8ランタイム）。TypeScript化はしない（要件定義書6章: clasp のビルドが複雑になり非エンジニア閲覧者のハードルが上がるため）
- フレームワーク: なし（Google Apps Script のコンテナバインドスクリプト、Webアプリ化はスコープ外）
- DB: なし。Google スプレッドシート自体をデータストアとして使う（シート構成は要件定義書3章）
- テスト: 自動テストフレームワークは導入しない（要件定義書10章で明示的にスコープ外）。検証は `npm run lint` と、要件定義書9章の手動シナリオ（スプレッドシート上のカスタムメニューから実行）で行う
- デプロイ: `clasp push` でスクリプトエディタに反映。ユーザーは Google アカウントのみで動作、追加費用なし

## コマンド
```bash
npm install       # 依存インストール（@google/clasp, eslint）
npm run dev        # clasp push --watch（保存のたびに反映）
npm run lint       # eslint src（唯一の自動検証。GASグローバルは eslint.config.js の globals.googleappsscript で許可）
npm run push       # clasp push（型チェック/ビルドに相当する検証。src/ の構文エラー等はここで露呈する）
npm run open       # clasp open（スクリプトエディタをブラウザで開く）
```
`clasp` 未ログインの場合は `npm run login` が必要（要 Google アカウント認証・ブラウザが開く）。
`.clasp.json` は各自 `clasp create`（新規）または `clasp clone <scriptId>`（既存）で生成する。`.clasp.json.example` を参考に `rootDir: "./src"` を指定すること。`appsscript.json` は clasp の仕様上 `rootDir` と同階層（= `src/`）に置いてある（要件定義書7章の図ではプロジェクト直下だが、clasp はマニフェストを rootDir 内にしか認識しないためこの構成にした）。

## プロジェクト構成
```
src/
├── appsscript.json    # マニフェスト（timeZone, oauthScopes等）
├── main.js            # onOpen、カスタムメニュー、各トリガーのエントリポイント
├── setup.js           # 初期セットアップ（シート生成・書式・トリガー登録、冪等）
├── config.js          # 「設定」シートの読み込みとバリデーション
├── inquiry.js         # 新規受付処理（ID採番・担当者割当・期限計算）
├── reminder.js         # 日次リマインド（バッチ処理・継続トリガー・エスカレーション）
├── notify.js           # メール/Slack送信・テンプレート展開・テストモード分岐
├── businessDays.js     # 営業日計算（設定シートの営業日/休業日を考慮）
├── logger.js           # 「実行ログ」シートへの記録・ログローテーション
└── constants.js        # シート名・列番号などの定数（列番号を直書きしない）
docs/
└── demo.gif            # README用の動作GIF（Day3で追加）
```

## ハマりどころ・既知の問題（随時追記・消さない）
- clasp の `rootDir` は `appsscript.json` と同じ階層でなければ認識されない。要件定義書7章のツリー図はマニフェストをプロジェクト直下に置いているが、実際は `src/appsscript.json` にしてある（上記「コマンド」参照）。
- `getRange().getValue()` をループ内で呼ぶと極端に遅い＆6分制限に抵触しやすい。必ず `getValues()`/`setValues()` の一括処理にする（要件定義書6.2章）。
- 日次リマインドは6分の実行時間制限があるため、4分30秒で安全中断→継続トリガーで再開という設計が必須（要件定義書6.1章）。ここを端折ると500件規模のサンプルデータで動作確認シナリオ6番が失敗する。
- **GAS の V8ランタイムは全ファイルが1つのグローバルスコープを共有するが、トップレベルで見えるのは `var` と関数宣言だけ。`let`/`const` はファイルごとに閉じてしまい他ファイルから参照できない。** 新しい定数・共通関数はトップレベルで必ず `var`/`function` で宣言すること（`constants.js` は全部 `var` にしてある）。
- 上記の裏返しで、ESLint はファイル単位でしか解析しないため `eslint.config.js` の `projectGlobals` に列挙していない識別子を他ファイルから参照すると `no-undef` が誤検知する。新しいトップレベル `var`/関数を追加したら `eslint.config.js` の `projectGlobals` にも追記すること。
- 上記と表裏で、他ファイルから参照されるトップレベル `var`/関数は `npm run lint` で `no-unused-vars` の**警告**が出る（そのファイル単体では未使用に見えるため）。これは想定内の誤検知なので無視してよい。`no-undef` の**エラー**が0件であることだけを見ればよい。

## 検証ループ（最重要・消さない）
- **IMPORTANT: コードを変更したら必ず `npm run lint` を実行し、エラーが無いことを確認する。** GAS には自動テストが無いため、これと `npm run push`（構文エラーの検出）が唯一の自動検証。
- 機能単位の実装が終わったら、要件定義書9章の該当シナリオを実際にスプレッドシート上（カスタムメニュー）で手動実行し、結果を確認する。特にシナリオ6（500件・6分制限対応）は省略しない。
- コミットは論理的な区切りで分ける（要件定義書12章: 一括コミットは避ける）。
- 成功を主張する前に証拠を示す（lint の出力、手動シナリオの実行結果）。

## やってはいけないこと（境界・消さない）
- **YOU MUST NOT: `.env` や `.clasp.json`（scriptId）・認証情報をコミットしない。**
- スコープ外の大規模リファクタはしない。ただし根本原因の修正に必要な隣接コードは触ってよい。
- 要件定義書10章のスコープ外項目（Webアプリ化、認証・権限管理、添付ファイル処理、返信メール自動取込、多言語対応、外部DB連携、単体テストフレームワーク導入）には手を出さない。
- 設定値をコードにハードコードしない。すべて「設定」シート経由にする（要件定義書12章）。
- 列番号を `src/*.js` に直書きしない。`constants.js` に集約する。
- 1件につき1通のリマインド送信は禁止（担当者ごとにまとめて1通、要件定義書F-03）。

## エージェントの動き方（ループエンジニアリング・消さない）
- **止まらない。途中で確認を求めない。** 仮定が必要なら合理的なベストを選び、何を仮定したか1行残して進む。
- ゴール未達・エラー発生いずれも止まらない。次の手を自分で決めて続行する（テスト修正・別アプローチ・追加調査など）。
- 数字・日付・仕様はファイルに根拠がない限り使わない。根拠がなければ「仮定:」と明記して進む。
- 複数ファイルにまたがる変更は、プランを先に `.claude/plan.md` へ書いてから実行する。
- ループ中に得た知見・進捗・試みたことは `.claude/loop-result.md` に随時記録する。
- **ループ中にプロジェクト固有の罠を発見したら、即座に「ハマりどころ」セクションに追記する。** 次のループが同じミスを繰り返さない。
- 実装と検証は分離する。実装後は別サブエージェント（Agent tool）に検証・レビューを依頼してよい。Antigravityが使える場合の追加レビューは下記「Antigravityへのセカンドオピニオンレビュー」参照。
- 実装は要件定義書11章の Day1→Day2→Day3 の順で進める。各フェーズの終わりで動作確認を行い、動く状態でコミットする。

### 停止条件（これ以外は止めない）
1. **完了**: 要件定義書9章の動作確認シナリオ（1〜7）がすべて通り、`npm run lint` がエラー無しで、README（8章の構成）が埋まっている状態
2. **試行上限**: 10ターン超えても前進なし → 原因と試みたことを `.claude/loop-result.md` に書いて停止（仮定: 具体的な上限の根拠ファイルは無いため妥当な値を仮置き）

### GitHub Issue運用（消さない）
- **ユーザーからコード変更を伴う依頼を受けたら**: まず `gh issue create` で記録してから、そのままいつも通り実装する。質問・説明だけの依頼はIssue化しない。完了したら `gh issue comment` で内容と検証結果を報告し `gh issue close` で閉じる。
- **作業中にスコープ外の問題を見つけたら**: 直さず `gh issue create` で記録するだけにして、今のタスクを続ける（「やってはいけないこと」の対象外リファクタの具体化）。
- **溜まったIssueをまとめて実行するとき**: `/work-issues` を使う。open issueを順に確認し、実行が必要なものだけ計画→実装→verifierサブエージェントで検証→コミット→pushし、`gh issue comment`+`close`する。検証が試行上限を超えて失敗したら `blocked` ラベルを付けて次のIssueへ進む（次回実行時はスキップされる）。

### Antigravityへのセカンドオピニオンレビュー（任意・消さない）
- `.mcp.json` の `antigravity` サーバー（`mcp__antigravity__ask_antigravity` 等）が使える場合、実装後のverifierサブエージェントによるレビューに加えて、`ask_antigravity` に同じ差分を見せて独立した意見をもらってよい。別モデル（Gemini系）にレビューさせることで、Claude同士のレビューでは拾いにくい見落としを狙う。
- 使うのはレビューフェーズのみ。`delegate_task`（Antigravityに実装そのものを任せる機能）はこのプロジェクトでは使わない。実装は常にClaude Codeが行う。
- MCPサーバーが未接続（`ToolSearch` で見つからない）場合は無視してよい。必須の検証手段ではなく、verifierサブエージェントのレビューだけでも「検証ループ」の要件は満たす。
