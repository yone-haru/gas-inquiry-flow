# 設計ドキュメント：問い合わせ管理・自動通知システム（Google Apps Script）

## 1. 解決する課題

小規模事業者が Google フォームで問い合わせを受けている状況を想定する。回答はスプレッドシートに溜まるが、以下の問題が起きる。

1. 新しい問い合わせに気づかず、返信が数日遅れる
2. 誰が対応するのか決まっておらず、放置される
3. 対応済みかどうかが分からず、二重連絡や対応漏れが発生する

このシステムは、フォーム受付から担当者への通知、未対応案件のリマインドまでを自動化し、**担当者が毎朝スプレッドシートを確認する運用をなくすこと**を目的とする。

---

## 2. 全体の動作

1. フォームが送信されると、行に管理 ID・ステータス・担当者・対応期限が自動で付与される
2. 種別に応じた担当者へ、メールまたは Slack で即座に通知が飛ぶ
3. 毎朝決まった時刻に、未対応かつ期限が近い案件を集計し、担当者ごとにリマインドを送る
4. 期限を過ぎた案件は管理者にもエスカレーション通知が飛ぶ
5. すべての挙動は「設定」シート上で変更でき、コードを触る必要がない

---

## 3. スプレッドシート構成

シートは 5 枚。すべてスクリプトから自動生成される（F-01 参照）。

### 3.1 「問い合わせ一覧」シート

フォームの回答先シートを想定。A〜E 列はフォームが生成し、F 列以降をスクリプトが管理する。

| 列 | 項目名 | 生成元 | 内容 |
|---|---|---|---|
| A | タイムスタンプ | フォーム | 受信日時 |
| B | お名前 | フォーム | |
| C | メールアドレス | フォーム | |
| D | 種別 | フォーム | 見積依頼 / 不具合報告 / その他（選択式） |
| E | 内容 | フォーム | 自由記述 |
| F | 管理ID | スクリプト | `INQ-20260829-001` 形式。日付ごとに連番 |
| G | ステータス | スクリプト | 未対応 / 対応中 / 完了（プルダウン、初期値は未対応） |
| H | 担当者 | スクリプト | 「担当者」シートから自動割当 |
| I | 対応期限 | スクリプト | 受信日 + 種別ごとのSLA日数（営業日ベース） |
| J | 初回通知日時 | スクリプト | |
| K | 最終リマインド日時 | スクリプト | 同日の重複送信を防ぐために使用 |
| L | 完了日時 | スクリプト | ステータスが完了に変わった時点で記録 |
| M | 備考 | 手入力 | |

ステータス列にはプルダウンと条件付き書式を設定してある（未対応=赤、対応中=黄、完了=グレー）。担当者が見た瞬間に状況が分かることを狙っている。

### 3.2 「設定」シート

A 列に設定キー、B 列に値、C 列に説明。この形式で固定してある。非エンジニアが B 列だけを書き換えて運用できることが、このシステムの中心的な設計方針である。

| 設定キー | 初期値 | 説明 |
|---|---|---|
| 通知方法 | メール | メール / Slack / 両方 |
| Slack Webhook URL | （空） | Slack を使う場合のみ入力 |
| 管理者メールアドレス | （空） | エラー通知とエスカレーションの送信先 |
| リマインド実行時刻 | 9 | 0〜23 の整数 |
| SLA日数_見積依頼 | 1 | 営業日 |
| SLA日数_不具合報告 | 1 | 営業日 |
| SLA日数_その他 | 3 | 営業日 |
| 営業日 | 月,火,水,木,金 | カンマ区切り |
| 休業日 | （空） | `2026-12-29,2026-12-30` のような日付のカンマ区切り |
| リマインド対象日数 | 1 | 期限まで何日以内の案件を通知するか |
| テストモード | TRUE | TRUE の間は実際には送信せずログのみ記録 |
| ログ保持行数 | 1000 | これを超えたら古い行から自動削除 |

読み込み時にバリデーションを行い、不正な値があれば「設定」シート上でセルを赤くし、何が問題かを明示する。エラーを黙って握りつぶさない設計にしている。

### 3.3 「担当者」シート

| 列 | 項目名 | 内容 |
|---|---|---|
| A | 種別 | 見積依頼 / 不具合報告 / その他 |
| B | 担当者名 | |
| C | メールアドレス | |
| D | Slackメンション | `<@U01ABCDEFG>` 形式。任意 |
| E | 有効 | TRUE / FALSE |

同じ種別に複数人が登録されている場合はラウンドロビンで割り当てる。直近の割当位置は PropertiesService に保持する。該当者がいない場合は管理者に割り当てる。

### 3.4 「通知テンプレート」シート

| 列 | 項目名 |
|---|---|
| A | テンプレートID |
| B | 件名 |
| C | 本文 |

テンプレート ID は `新規受付` / `リマインド` / `期限超過` / `日次サマリ` の 4 種。

本文内では `{{管理ID}}` `{{お名前}}` `{{種別}}` `{{内容}}` `{{対応期限}}` `{{担当者名}}` `{{シートURL}}` をプレースホルダとして使える。未定義のプレースホルダが残っていた場合は空文字に置換し、ログに警告を出す。

### 3.5 「実行ログ」シート

| 列 | 項目名 |
|---|---|
| A | 日時 |
| B | 処理名 |
| C | 対象件数 |
| D | 結果 |
| E | メッセージ |

成功時も記録する。トラブル時にこのシートを見れば原因が分かる状態を目指している。

## 4. カスタムメニュー

スプレッドシートを開いたとき（`onOpen`）に「問い合わせ管理」メニューを追加する。非エンジニアがこのメニューだけで導入を完了できることを要件としている。

- **初期セットアップ** … 全シートの生成、ヘッダー・プルダウン・条件付き書式の設定、トリガーの登録までを一括実行
- **設定を確認** … 設定シートの値を検証し、結果をダイアログで表示
- **テスト通知を送る** … 現在の設定で通知が届くかを確認（1 件だけ送信）
- **リマインドを今すぐ実行** … 時刻を待たずに手動実行
- **サンプルデータを作成** … フォームがなくても動作確認できるダミー行を 20 件生成
- **トリガーを再設定** … 既存トリガーを削除して張り直す

初期セットアップは何度実行しても壊れない（冪等）。既存データがある場合は消さず、不足している要素だけを追加する。

## 5. 機能要件

### F-01 初期セットアップ
カスタムメニューから実行する。シート生成、書式設定、トリガー登録を行う。実行後、次に何をすべきか（設定シートの記入、テストモードの解除）をダイアログで案内する。

### F-02 新規受付処理
フォーム送信時トリガー（installable trigger）で起動する。管理 ID を採番し、担当者を割り当て、対応期限を計算し、担当者へ「新規受付」テンプレートで通知する。

対応期限は営業日ベースで計算する。土日と休業日をまたぐ場合は翌営業日に繰り越す。

### F-03 日次リマインド
時間駆動トリガーで毎日実行する。ステータスが「未対応」または「対応中」で、対応期限が設定日数以内に迫っている行を抽出し、担当者ごとにまとめて 1 通の通知にして送信する。1 件につき 1 通は送らない設計にしている（担当者の受信箱が溢れるため）。

同じ日に 2 回リマインドを送らないよう、K 列（最終リマインド日時）で判定する。

### F-04 期限超過エスカレーション
対応期限を過ぎた未完了案件は、担当者に加えて管理者にも通知する。

### F-05 完了処理
ステータスが「完了」に変更された行に、完了日時を自動記録する（`onEdit` トリガー）。

### F-06 テストモード
設定シートの「テストモード」が TRUE の間、メールと Slack への送信を行わず、送信予定の内容を実行ログに記録するだけにする。導入検証時の誤送信を防ぐための機能である。

## 6. 技術要件

### 6.1 6 分の実行時間制限への対応

日次リマインドは対象行数が増えると 6 分制限に達する。以下の方式で対応している。

- 100 行単位のバッチで処理する
- 処理開始から 4 分 30 秒が経過した時点で安全に中断する
- 中断位置（カーソル）を PropertiesService に保存する
- 1 分後に起動する継続トリガーを動的に生成し、次回はカーソル位置から再開する
- 全件処理が終わったらカーソルを削除し、継続トリガーも削除する

この仕組みは README にも図解付きで記載している。

### 6.2 スプレッドシートアクセスの最適化

`getRange().getValue()` をループ内で呼ぶ実装は避ける。`getValues()` で一括取得し、メモリ上で処理し、`setValues()` で一括書き込みする方針にしている。

### 6.3 排他制御

`LockService.getScriptLock()` を使い、フォーム送信と日次リマインドが同時に走った場合の競合を防ぐ。待機は最大 30 秒、取得できなければログに記録して終了する。

### 6.4 冪等性

同じ処理が二重に走っても、通知が重複しない。判定は J 列・K 列の日時で行う。

### 6.5 エラーハンドリング

すべての外部呼び出し（メール送信、Slack への UrlFetch）を try-catch で囲む。失敗しても処理全体を止めず、その行をスキップして続行し、ログに記録する。

管理者へのエラー通知は 1 日 1 通までに制限している（PropertiesService で送信済みフラグを管理）。エラー通知で受信箱が埋まると実運用で無効化されてしまうため。

### 6.6 Slack 送信

Incoming Webhook を使用する。UrlFetchApp で POST し、`muteHttpExceptions: true` でレスポンスコードを確認する。失敗時はメールにフォールバックする。

## 7. ファイル構成

clasp でローカル管理し、GitHub にコミットできる形にしている。

```
gas-inquiry-flow/
├── README.md
├── .clasp.json.example
├── appsscript.json
├── src/
│   ├── main.js          # onOpen, トリガーから呼ばれるエントリポイント
│   ├── setup.js         # 初期セットアップ、シート生成
│   ├── config.js        # 設定シートの読み込みとバリデーション
│   ├── inquiry.js       # 新規受付処理、ID採番、担当者割当
│   ├── reminder.js      # 日次リマインド、バッチ処理、継続トリガー
│   ├── notify.js        # メール/Slack送信、テンプレート展開
│   ├── businessDays.js  # 営業日計算
│   ├── logger.js        # 実行ログ記録、ログローテーション
│   └── constants.js     # シート名、列番号などの定数
└── docs/
    └── demo.gif
```

列番号はコード内に直書きせず、`constants.js` に集約し、列の増減に耐えられる構造にしている。

各関数に JSDoc コメントを付ける。TypeScript 化はしていない（clasp のビルド設定が複雑になり、閲覧者にとってのハードルが上がるため）。

## 8. README の要件

想定読者は、GAS を知らない中小企業の担当者である。構成は以下の順序にしている。

1. 冒頭 1〜2 行で課題を提示する。技術の説明から始めない。「問い合わせの一次対応が遅れる、担当が決まらない、対応漏れが起きる。この 3 つを自動化で解決するツールです」のような書き出しにする
2. 動作 GIF を貼る。フォーム送信 → 通知が届く → リマインドが飛ぶ、の流れが 15 秒程度で分かるもの
3. できること（箇条書き 5 つ以内）
4. 導入手順（5 ステップ以内。スクリーンショット付き）
5. 設定シートの説明（表形式。3.2 章の内容）
6. カスタマイズ方法（通知文面の変え方、担当者の追加方法。コードを触らずにできることを明示する）
7. 技術的な工夫（6 分制限の回避方法をここに書く。図があると良い）
8. 動作環境と費用（Google アカウントのみで動作、追加費用なし、GAS の無料枠内で収まることを明記）
9. 制約事項（1 日あたりのメール送信上限など）

「導入手順」は、初期セットアップメニューを押すだけで大半が完了する状態を目指している。手順が長くなるほど非エンジニアは離脱しやすいため。

## 9. 動作確認シナリオ

以下のシナリオで動作確認する。

1. 空のスプレッドシートで「初期セットアップ」を実行 → 5 シートが生成され、トリガーが登録される
2. 「サンプルデータを作成」を実行 → 20 件のダミー行が入り、管理 ID・担当者・期限がすべて埋まる
3. テストモードのまま「リマインドを今すぐ実行」 → 実行ログに送信予定内容が記録され、実際には送信されない
4. テストモードを FALSE にして再実行 → 実際に通知が届く
5. 設定シートの「SLA日数_見積依頼」に文字列を入れる → セルが赤くなり、エラーが表示される
6. サンプルデータを 500 件に増やして実行 → 途中で中断し、継続トリガーで再開して完走する
7. 「初期セットアップ」を 2 回実行 → データが失われない

6 番目は 6 分制限対応の検証にあたる。

## 10. スコープ外

以下はスコープ外としている。

- Web アプリ化、独自 UI の構築
- ユーザー認証、権限管理
- 添付ファイルの処理
- 返信メールの自動取り込み
- 多言語対応
- 外部データベースとの連携
- 単体テストフレームワークの導入（GAS では構築コストに見合わない）

## 11. 進め方

1 日ずつ区切って実装を進めた。各フェーズの終わりで動作確認を行い、動く状態でコミットしている。

**Day 1** … 定数定義、設定読み込みとバリデーション、初期セットアップ、シート生成、サンプルデータ生成

**Day 2** … 新規受付処理、営業日計算、通知（メール / Slack）、テンプレート展開、実行ログ

**Day 3** … 日次リマインド、バッチ処理と継続トリガー、エスカレーション、テストモード、README と GIF

---

## 12. 実装時の注意

- 設定値はコードにハードコードせず、すべて設定シート経由にしている
- 日本語の変数名は使わず、シート名・列名・設定キーのみ日本語のままにしている（利用者が読む部分のため）
- エラーメッセージは日本語で、何をすれば直るかまで記載する。「エラーが発生しました」のみの表示はしない
- コミットは機能単位で分割する。一括コミットは避ける
- README は Day 1 の時点で骨子を作り、実装しながら埋めていく方針にした
